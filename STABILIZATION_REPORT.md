# HakbangHero stabilization — 15 November 2026

Firebase remains on Spark. No Cloud Functions or billing changes are included. Rules enforce bounded duel payouts and immutable receipts; physical movement remains client-reported and cannot be securely attested by rules. Two cooperating modified clients could fabricate plausible reports. This is the accepted limitation of the Spark design.

## Platform export destinations

- Android Save Image opens the system document picker. The user chooses a destination such as Downloads or another Files provider. This does not automatically insert into Gallery. Share hands the PNG file to the Android system share sheet; an external app controls subsequent publication.
- iOS Safari uses file sharing when `navigator.canShare` permits the prepared PNG. Otherwise Save Image requests an actual Blob image download; Open Image opens the PNG for Safari's share/image menu, allowing Save to Files or Photos. A download request or share-sheet handoff is never reported as confirmed storage/publication.
- Browser cancellation is reported as cancellation. Unsupported capabilities expose the actual download/open fallback. Repeated taps cannot overlap export operations.

## Firebase scope and compatibility

`firebase.json` deploys `firestore.rules`, not `firestore_round2.rules`. The initial deployed rules matched the original local file. The generated rules and template are synchronized by `tools/gen_economy_rules.py`. Existing descending leaderboard indexes are retained; no new indexes are required for the repaired queries.

New invitations include `reward_protocol: 2`; finalized rewards create `duel_reward_receipts/{challengeId}`. Existing user data, run history and completed duels are preserved. There is no database reset or bulk migration. Old open clients should refresh. Older Android binaries do not implement the new settlement protocol and must be rebuilt/released before relying on new duel payouts. In-flight older duels may need to end without a reward rather than bypass the new protections.

## Device acceptance checklist

1. On Android release and iPhone Safari, manually sign up, refresh during profile/consent/BMI steps, retry after network interruption, and sign back in. Confirm one profile/name claim, preserved stats and the correct next screen. Repeat with Google; inspect the release signing certificate if Google rejects Android authentication.
2. With two dedicated accounts on separate devices, invite from each eligible screen; test busy/offline, decline and same-direction cooldown, reverse invitation, expiry, cancellation, simultaneous invitations, accept/ready/countdown, reconnect and refresh. Confirm both screens converge.
3. Complete a real outdoor duel with continuous accurate GPS. Verify one receipt and one capped payout. Trigger approved unrealistic-motion evidence in a controlled test and verify invalidation/no rewards on both clients. A missing coverage report must fail closed without a reward.
4. Complete and save a normal run, refresh, and confirm one history item plus one XP/coin/leaderboard update. Retry an interrupted save and verify no duplicate award.
5. Export that saved summary: Android Share and document-picker Save; Safari file share, cancellation, download and Open Image. Inspect the resulting readable PNG and chosen storage destination. Tap repeatedly and navigate away during handoff; no duplicate exports or rewards.
6. Check narrow-screen layouts, costume collapse/recent order, reduced motion and zoom. Profile a release tracking session on a physical phone, then close the screen and verify location/ticker work stops as intended.

## Files changed

Realtime/update follow-up: the inbox's `members arrayContains uid` collection query did not match the additional document-ID predicate in the chat read rule. Rules now distinguish direct gets (ID + member checks) from collection lists (member check provable by the query); chat writes retain their existing ID/member and friendship validation. The template is updated too. Inbox listener errors are logged and retried, notifications compare server timestamps rather than phone time, and ChatScreen holds one stable metadata-aware message stream. The web entry page unregisters only legacy same-origin Flutter service workers and reloads before bootstrapping, without clearing auth or IndexedDB. Read-only network comparisons confirmed both Hosting domains served the previous release exactly; that did not establish what a device's service worker was serving. No tests or test messages were requested/run for this follow-up. Installed Android binaries still require a newly built APK; Hosting updates affect Android browsers/PWAs, not native binaries.

This follow-up's release web build succeeded and the targeted rules plus Hosting were deployed on 15 November 2026, approximately 12:03 Manila time.
